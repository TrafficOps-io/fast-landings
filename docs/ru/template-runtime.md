# Данные HTTP-запроса, валидация и PHP

Эта часть документации объясняет, как читать данные посетителя, проверять форму и выполнять PHP в опубликованном лендинге. Начните с [руководства по шаблонам](templates.md); объявления настроек, блоков и циклов описаны в [справочнике DSL](template-dsl.md).

## Когда подставляются значения

У шаблона две фазы работы:

| Фаза | Что происходит | Пример |
| --- | --- | --- |
| Создание или обновление релиза | Проверяются сохранённые настройки, раскрываются блоки и циклы, подставляются `{{…}}`. Макросы запроса и правила валидации компилируются в PHP. | `{{title}}` берёт заголовок из настроек лендинга. |
| Каждый HTTP-запрос к опубликованной странице | PHP читает запрос, проверяет правила страницы и подставляет `{query.…}`, `{headers.…}`, `{body.…}`. | `{body.name}` берёт имя из текущей отправки формы. |

Например, объявление настройки:

```html
@param message Text = "Спасибо, {body.name}!"
```

и разметка `<p>{{message}}</p>` сохраняют возможность менять текст в панели. Значение `{body.name}` вычисляется заново для каждого посетителя. Полученная от посетителя строка не проходит повторную интерполяцию: если имя содержит `{query.secret}` или PHP-код, это останется текстом.

Правила `@validation` задаются в исходном файле. Текст настройки не может добавлять новые правила или PHP-код. Параметры внутри `@validation` не создают поля формы настроек.

## Источники и пути

| Синтаксис | Источник |
| --- | --- |
| `{query.subid}` | Параметр URL из `$_GET`, например `?subid=demo`. |
| `{headers.user-agent}` | Заголовок запроса. Регистр имени не имеет значения: `{headers.X-Client}` и `{headers.x-client}` эквивалентны. |
| `{body.name}` | Поле тела запроса: POST-форма или JSON. |
| `{body.customer.name}` | Вложенное поле `customer.name`. |
| `{body.items.0.name}` | Поле `name` первого элемента массива `items`. |
| `{query.*}`, `{headers.*}`, `{body.*}` | Весь соответствующий источник в виде JSON с HTML-экранированием. |

Макросы работают и без `@validation`. Объявляйте правила отдельно, если значение обязательно или должно иметь заданный формат.

Имена источников пишутся строчными буквами. Сегмент пути начинается с ASCII-буквы, цифры или `_`, далее допускает также `-`; сегменты разделяются точкой. Пробелы, квадратные скобки и выражения в макросе не поддерживаются. Звёздочка разрешена только вместо всего пути: `{body.*}`, но не `{body.customer.*}`.

Точка означает переход к вложенному объекту или массиву. Для формы используйте `name="customer[name]"`, а для JSON — `{"customer":{"name":"Игорь"}}`. JSON-ключ `"customer.name"` не читается через `{body.customer.name}`: синтаксиса экранирования точки в ключе нет. Индекс массива пишется числом через точку. Имена query/body чувствительны к регистру. Заголовки приводятся к нижнему регистру; `Content-Type` и `Content-Length` также доступны.

### Формы, JSON и HTTP-методы

`query` и `body` независимы: query-параметр не заменяет отсутствующее поле тела. Форма с `method="get"` передаёт поля в `query`. Обычная форма с `method="post"` передаёт их в `body`, включая вложенные поля стандартной PHP-нотации `customer[name]`.

Для тела есть два режима:

- При `Content-Type: application/json` или `application/…+json` читается `php://input`. Параметр `charset` допускается; например, `application/json; charset=UTF-8`. Корень JSON должен быть объектом или массивом. Вложенность декодируется с лимитом 64; большие целые, не помещающиеся в PHP integer, сохраняются строками.
- Для остальных типов содержимого используются данные `$_POST`: в частности, POST-формы `application/x-www-form-urlencoded` и текстовые поля `multipart/form-data`. Файлы находятся в PHP `$_FILES` и не входят в `{body.*}`. Сам runtime не разбирает произвольный текст, XML или URL-encoded тело PUT/PATCH.

JSON читается независимо от метода запроса. Сам `@validation body` не требует POST и не ограничивает список HTTP-методов. Если обработчик должен принимать только POST, проверяйте метод в PHP.

Невалидный JSON, пустое JSON-тело и JSON со скалярным корнем (`"text"`, `42`, `true`, `null`) дают пустой `body`. Если страница содержит хотя бы один блок `@validation body`, такой запрос провалит его даже при необязательных параметрах. Без проверки `body` автоматического ответа с ошибкой не будет. Проверки только `query` или `headers` сами по себе JSON не отклоняют.

### Вывод и экранирование

| Значение | Результат подстановки |
| --- | --- |
| Поле отсутствует или равно JSON `null` | Пустая строка. |
| Строка или число | Исходное значение, преобразованное в текст. |
| JSON `true` / `false` | Текст `true` / `false`. |
| Массив или объект | JSON; различие между `{}` и `[]` сохраняется. |

Затем результат проходит HTML-экранирование: `<`, `>`, `&`, одинарная и двойная кавычки не превращаются в разметку. Например, имя `<Игорь>` выводится как `&lt;Игорь&gt;` в исходном HTML. Некорректные UTF-8-последовательности заменяются при выводе; правило `String` отклоняет их при валидации.

Чтобы показать посетителю буквальный макрос, напишите `\{body.name}`. Двойные скобки `{{name}}` относятся к настройкам шаблона, а не к данным запроса.

## Где можно использовать макросы

Поддерживаются HTML-текст и значения атрибутов в одинарных или двойных кавычках:

```html
<p>Здравствуйте, {body.name}!</p>
<input name="subid" value="{query.subid}">
<main data-pixel="{query.pixel}" data-client="{headers.x-client}"></main>
<a href="https://example.com/offer?subid={query.subid}">Продолжить</a>
```

В URL-атрибутах перед макросом нужен статический префикс: `http://`, `https://`, `/`, `./`, `../`, `#`, `?` либо относительный путь с `/`, `?` или `#`. Например, `href="/offers/{query.id}"` и `href="success.php?subid={query.subid}"` поддерживаются. Полностью динамический `href="{query.url}"` отклоняется. Для настройки типа `Url` дополнительно действуют её собственные правила, описанные в [справочнике DSL](template-dsl.md).

HTML-экранирование не кодирует компоненты URL. Например, `&` внутри значения может стать разделителем query-параметров после чтения атрибута браузером. Для произвольных значений собирайте URL через PHP `http_build_query()`/`rawurlencode()` или JavaScript `URL`/`URLSearchParams`.

Во время проверки или публикации отклоняются макросы:

- внутри `<script>` и `<style>`;
- в обработчиках событий (`onclick` и других `on…`), `style`, `srcdoc`, `srcset`;
- в атрибутах без кавычек, именах тегов и вместо набора атрибутов;
- в `content` у `<meta http-equiv="refresh">`;
- в атрибутах SVG-анимаций `animate`, `set`, `animateMotion`, `animateTransform`, `animateColor`.

Передавайте данные JavaScript через `data-*` и обращайтесь к ним как к тексту:

```html
<p id="greeting" data-name="{body.name}"></p>
<script>
  const greeting = document.getElementById('greeting');
  greeting.textContent = `Здравствуйте, ${greeting.dataset.name}!`;
</script>
```

## Блок `@validation`

Размещайте проверки на уровне страницы, перед `@layout`:

```html
@validation query fallback="/error.html"
  @param subid String required min=1 max=120
@endvalidation
@validation headers
  @param X-Client String required
@endvalidation
```

Первый аргумент — `query`, `headers` или `body`. Единственная опция блока — `fallback`. Внутри допустимы только `@param` и пустые строки; нужен хотя бы один параметр. Вложенные блоки запрещены. Одно имя нельзя объявлять дважды для одного источника на одной странице, в том числе в разных блоках. Для заголовков дубликаты сравниваются без учёта регистра. Одинаковые имена в разных источниках или на разных страницах допустимы.

Правила принадлежат странице, где объявлены. Проверка тела на `success.php` не мешает GET-запросу к `index.php`. Блоки проверяются по порядку, до вывода HTML и выполнения обычного PHP-кода страницы. Первая неудачная проверка немедленно завершает обработку; последующие блоки и код страницы не выполняются. Проверяются только объявленные параметры: дополнительные поля запроса разрешены.

### Типы запроса

Типы здесь ограничены четырьмя именами. Пользовательские типы DSL, `Text`, `Email`, `Url` и типы массивов использовать нельзя.

| Тип | Что принимается для непустого значения |
| --- | --- |
| `String` | Только корректная UTF-8-строка. Число из JSON не преобразуется в строку. |
| `Number` | PHP-число или числовая строка с конечным значением. Например, `2`, `"2.25"`, `"1e3"`. Boolean и `"INF"` не подходят. |
| `Integer` | PHP integer либо строка из цифр с необязательным начальным `+`/`-`. Строки `"2.0"`, `"1e3"`, `" 2 "` и JSON-число `2.0` не подходят. |
| `Boolean` | JSON/PHP boolean, целое `0`/`1` или одна из строк `"0"`, `"1"`, `"true"`, `"false"`. Строки `"yes"`, `"on"`, `"TRUE"` не подходят. |

Проверка не меняет данные: `"001"` после успешного `Integer` остаётся текстом `001`, а `"0"` после `Boolean` выводится как `0`. Для checkbox задавайте `value="1"`, если проверяете его как `Boolean`: стандартное браузерное значение `on` не принимается.

### Правила параметра

```html
@validation body
  @param customer.name String required min=2 max=80
  @param phone String required mask="+380 ... ... ..."
  @param code String length=6
  @param amount Number min=0.01 max=100000
  @param quantity Integer required min=1 max=20
  @param consent Boolean required
@endvalidation
```

| Опция | Значение |
| --- | --- |
| `required`, `required=true` | Поле обязательно. Отсутствие, `null`, пустая строка или строка, которую PHP `trim()` делает пустой, не допускаются. Значения `0` и `false` считаются присутствующими. |
| `required=false` | Значение по умолчанию: отсутствующее или пустое поле пропускает остальные правила. |
| `min`, `max` | Включительные границы. Для `String` это длина в Unicode-символах; для `Number`/`Integer` — числовое значение. Для `Boolean` запрещены. |
| `length` | Точная длина строки. Принимается также исторический псевдоним `lenght`, но в новых шаблонах используйте `length`. |
| `mask` | Маска всей строки: каждая `.` соответствует одной ASCII-цифре `0–9`, остальные символы совпадают буквально. Это не регулярное выражение. |

Для строк `min`, `max` и `length` должны быть неотрицательными целыми; длина считается по Unicode-кодовым точкам, а не байтам. У составных символов с комбинируемыми знаками может быть больше одной кодовой точки. Для числовых границ нужны конечные числа; `min` не может превышать `max`. `length` должна находиться внутри заданного диапазона. `length` и `mask` разрешены только у `String`.

Маска должна быть непустой UTF-8-строкой без NUL, не длиннее 1000 байт. Маска `"+380 ... ... ..."` принимает `+380 123 456 789`, но отклоняет другой формат пробелов, буквы и добавочные символы.

У необязательного параметра пустая строка не проверяется на `min`, `length` или `mask`. Пробелы автоматически не удаляются и при выводе сохраняются. Нет опций `default`, `nullable`, преобразования типа или собственных сообщений об ошибке. Повторение опции, неизвестная опция или противоречивые границы — ошибка исходника.

### Ответ при ошибке и `fallback`

| Настройка блока | Ответ на невалидный запрос |
| --- | --- |
| `fallback="/error.html"` | Заголовок `Location` со статусом `302` для GET/HEAD или `303` для остальных методов. HTML страницы не выводится. |
| Без `fallback` | Статус `422`, `Content-Type: text/plain; charset=UTF-8`, текст `Invalid request.`. |

`fallback` — фиксированный локальный URL: абсолютный путь `/error.html` или относительный `submit-error.html`, в том числе с query/fragment. Существование целевой страницы не проверяется: добавьте её в ZIP или укажите существующую страницу. Относительный адрес разрешается браузером относительно текущего URL. После `303` браузер открывает адрес методом GET; поля исходного POST автоматически не переносятся.

Внешние URL, адреса с `//`, обратной косой чертой, пробелами или управляющими символами запрещены. Проверяется также percent-encoding, чтобы, например, `/%2Fevil.example` не превратился во внешний адрес. Runtime-макросы в `fallback` не подставляются. Выбирайте адрес, чьи собственные правила позволят открыть страницу после редиректа, чтобы не получить цикл.

## Полный пример: форма и результат

Создайте два файла в одной папке. Первый файл — `index.tpl.html`:

```html
@template "Форма обратного звонка" version=1
@param title String = "Заказать звонок"
@validation query
  @param subid String max=120
@endvalidation
@layout
<!doctype html>
<html lang="ru">
<head><meta charset="utf-8"><title>{{title}}</title></head>
<body>
  <h1>{{title}}</h1>
  <form action="success.php" method="post">
    <input type="hidden" name="subid" value="{query.subid}">
    <label>Имя <input name="customer[name]" required minlength="2" maxlength="80"></label>
    <label>Телефон <input name="phone" required placeholder="+380 123 456 789"></label>
    <button type="submit">Отправить</button>
  </form>
</body>
</html>
@endlayout
```

Второй файл — `success.tpl.php`:

```html
@param message Text = "Спасибо, {body.customer.name}! Позвоним на номер {body.phone}."
@validation body fallback="index.php"
  @param customer.name String required min=2 max=80
  @param phone String required mask="+380 ... ... ..."
  @param subid String max=120
@endvalidation
@layout
<!doctype html>
<html lang="ru">
<head><meta charset="utf-8"><title>Спасибо</title></head>
<body>
  <h1>Заявка принята</h1>
  <p>{{message}}</p>
  <p>Идентификатор: {body.subid}</p>
</body>
</html>
@endlayout
```

В этой папке выполните:

```sh
zip callback-template.zip index.tpl.html success.tpl.php
```

Импортируйте ZIP как шаблон и создайте из него лендинг по [руководству](templates.md). В релизе появятся `index.php` и `success.php`. Заголовок и сообщение будут настройками лендинга; параметры запроса — нет. Откройте опубликованный сайт с `?subid=demo` и отправьте имя `Игорь` с телефоном `+380 123 456 789`.

Те же запросы можно проверить через `curl`, заменив адрес на домен лендинга:

```sh
LANDING_URL='https://landing.example'

curl -i "$LANDING_URL/?subid=demo"

curl -i "$LANDING_URL/success.php" \
  --data-urlencode 'customer[name]=Игорь' \
  --data-urlencode 'phone=+380 123 456 789' \
  --data-urlencode 'subid=demo'

curl -i "$LANDING_URL/success.php" \
  -H 'Content-Type: application/json' \
  --data '{"customer":{"name":"Игорь"},"phone":"+380 123 456 789","subid":"demo"}'

curl -i "$LANDING_URL/success.php" --data 'phone=invalid'
```

Первые три запроса возвращают `200`; две отправки выводят персональное сообщение. Последний запрос возвращает `303` с `Location: index.php`. Если открыть `success.php` обычным GET без тела, ответом будет `302` на ту же форму. Пример показывает приём и вывод данных; для сохранения заявки или отправки её в другой сервис добавьте PHP-обработчик после проверок.

## PHP в шаблоне

Для собственного PHP-кода используйте `.php` или `.tpl.php`. Само наличие `<?php … ?>` в статическом `.html` не меняет расширение файла и не включает выполнение PHP.

Фрагменты `<?php … ?>` и `<?= … ?>` сохраняются как PHP-код. Они не выполняются при импорте или компиляции и не разбираются как DSL. Даже `{{title}}`, `{body.name}` и `@validation` внутри PHP-строки останутся буквальным содержимым строки.

```html
@layout
<?php
$method = $_SERVER['REQUEST_METHOD'] ?? 'GET';
?>
<p>Метод: <?= htmlspecialchars($method, ENT_QUOTES, 'UTF-8') ?></p>
<p>Имя: {body.name}</p>
@endlayout
```

В PHP используйте обычные `$_GET`, `$_POST`, `$_FILES`, `$_SERVER` и `php://input`. Скомпилированный runtime не добавляет в PHP публичную переменную с декодированным JSON и не меняет суперглобальные массивы. Если нужен JSON внутри собственного кода, декодируйте его самостоятельно. Макросы читают снимок запроса, сделанный до выполнения вашего PHP; последующая правка `$_POST` не изменяет вывод `{body.name}`.

Страница может оставлять последний PHP-блок открытым; завершайте `@endlayout` на отдельной строке. Поддерживается размещение runtime после начальных `declare(strict_types=1)` и `namespace`, если PHP-открытие находится в самом начале страницы. Обычные companion-файлы `success.php` или `lib/helpers.php` могут не содержать DSL; `include`/`require` используют имена файлов релиза, например `success.php`, а не `success.tpl.php`.

Для выполнения нужен настроенный отдельный PHP runtime лендингов: см. [развёртывание](../../deploy/README.md#landing-php-behavior). Внутри него нет приложения панели и её Laravel-сервисов. Постоянное хранение заявок требует внешнего хранилища; опубликованные файлы лендинга доступны только для чтения.

## Публикация, предпросмотр и диагностика

Страница `.html` с макросами запроса или валидацией превращается в `.php`. Суффикс `.tpl` также убирается: `index.tpl.html` → `index.php`, `success.tpl.php` → `success.php`. Статическая HTML-страница без runtime остаётся HTML. Те же макросы и проверки можно использовать в обычном ZIP-лендинге без схемы настроек.

Ссылки и `action` лучше сразу писать на файлы релиза. Запрос к отсутствующей `.html`-странице может быть внутренне направлен в одноимённый `.php`, с сохранением query и тела POST; для production необходима актуальная конфигурация Caddy. Если результирующий путь конфликтует с другим файлом (например, динамический `success.html` и готовый `success.php`), публикация завершится ошибкой. Предыдущий активный релиз сохранится.

Исходники макросов сохраняются для редактора файлов в приватном служебном манифесте. Не добавляйте `.runtime-sources.json` в архив: путь зарезервирован.

Статический предпросмотр в панели и генератор скриншотов не исполняют PHP и не подставляют данные реального запроса. Они удаляют декларации валидации; макросы могут быть видны буквально. `previewData` содержит значения настроек, а не запрос посетителя. Для скриншота PHP-сайта используйте опубликованный `previewUrl`; реальную обработку формы проверяйте на опубликованном лендинге.

| Симптом | Что проверить |
| --- | --- |
| `Request validation:…` при импорте или публикации | Закрыт ли блок, допустимы ли типы/опции/границы, нет ли повторного параметра, безопасен ли `fallback` и HTML-контекст макроса. |
| Пустой вывод макроса | Выбран ли правильный источник, совпадает ли регистр, правильный ли вложенный путь, есть ли поле в запросе. |
| `422 Invalid request.` | Не выполнен блок без `fallback`. Подробности отдельных полей посетителю не выводятся. |
| `302` или `303` | Не выполнен блок с `fallback`; проверьте тело, заголовки и формат параметров. |
| `405` при отправке формы | Форма отправляет POST в статическую страницу; укажите PHP-обработчик или страницу с runtime. |
| `404` после перехода | Есть ли целевой файл/страница fallback в архиве; используется ли имя файла релиза. |
| PHP не выполняется или runtime недоступен | Проверьте конфигурацию PHP-FPM и маршрутизацию по инструкции развёртывания. |

Для проверки деталей реализации см. [`TemplateRequestRuntime`](../../app/Services/Templates/TemplateRequestRuntime.php), [unit-тесты runtime](../../tests/Unit/TemplateRequestRuntimeTest.php) и [интеграционные тесты](../../tests/Feature/TemplateRuntimeIntegrationTest.php).
